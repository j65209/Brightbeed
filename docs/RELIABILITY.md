# 동기화 안정화: 1차 변경과 운영 적용 기준

통신 성공, 수집 성공, 저장 성공을 구분한다. 화면에서 `완료`는 시작한 필수 작업이 모두 성공했을 때만 표시하며, 편집 중인 작업은 보류로 표시한다.

## 이번 변경

- HTTP 응답 본문까지 제한 시간을 적용한다. 터널 주소를 60초만 캐시하고, 프록시 읽기가 끊기면 주소를 갱신해 한 번 재조회한다. POST/PUT/PATCH/DELETE는 자동 재전송하지 않는다.
- 물류·보고서·아카이브·공지·연차·CS·MD 일정의 결과를 모두 기다린다. 하나라도 실패하거나 보류되면 전체 완료 시각을 갱신하지 않는다.
- 상태 응답이 없거나 45초 이상 조회되지 않은 에이전트는 확인 불가로 표시한다. 수동 직원은 요청 대기로 표시한다. `/agents/status` 자체의 실행 판정 정확성은 서버 변경이 추가로 필요하다.
- 수집 시각에 따라 물류/벤더는 30분, 매출/마케팅은 60분 이후 지연으로 표시한다. 벤더·캘린더는 수신 시각 대신 서버가 보내는 `X-Cache-Age`로 원본 시각을 계산하며, 헤더가 없으면 시각 미확인이다.
- 매출 카드의 30분 조회에 외부 플랫폼도 포함한다. 이는 브라우저가 열린 동안의 조회이며 서버의 수집 주기를 변경하지 않는다.
- 편집 가능한 JSON은 화면에 불러온 기준 내용과 현재 GitHub 내용이 같을 때만 저장한다. 저장 직전 또는 도중 충돌하면 멈추며 새 SHA로 전체 내용을 다시 덮어쓰지 않는다. 최신 내용을 불러오지 못한 상태의 저장도 보류한다.
- 발주 파서는 작업 잠금을 잡고, 일부 파일 오류·빈 결과·기존 10건 이상 데이터의 20% 초과 감소를 차단한다. 이전 파일을 `.last-good`로 보존한 뒤 임시 파일을 원자적으로 교체한다. 백업과 잠금 파일은 Git에 올리지 않는다.

## 검증

```sh
node --test tests/reliability.test.cjs
python3 -m unittest discover -s tests -p 'test_*.py'
```

테스트는 인위적인 실패 응답과 임시 폴더만 사용한다. 실제 회사 재고나 서버 스케줄은 변경하지 않는다. UI 초기 스크립트 문법, 응답 지연, 터널 변경, 쓰기 재전송 금지, 완료 표시, 편집 충돌, 에이전트 상태, 파싱 실패·중단·중복 실행을 검증한다.

## 운영에 반영하기 전

1. 이 변경을 테스트용 페이지에서 열고 실제 `/health`와 `/agents/status` 응답 형식을 확인한다. 원본 시각이 누락되면 수집 서버에서 보완한다.
2. 발주 파서가 서버 Mac에서 실행된다면 `parse_orders.py`와 `snapshot_store.py`를 함께 배치한다. GitHub에 병합하는 것만으로 서버 Mac 코드가 자동 갱신된다고 가정하지 않는다.
3. 파서는 복사한 입력 폴더/출력 파일로 먼저 실행해 실패 시 기존 정상본이 유지되는지 확인한다. 실제 발주서 삭제를 시험에 사용하지 않는다.
4. 기존 자연어 재고 직원 변경 PR은 별도 변경이다. 두 PR 모두 `agents.html`/`index.html`을 만지므로 적용 순서를 정하고 최신 main 위에서 충돌 해결·재검증한다.
5. 이상이 있으면 해당 코드 변경을 되돌린다. 데이터 파일은 백업의 생성 시각·건수·형식을 확인한 뒤 복구한다.

## 서버에서 남은 일

현재 접근 가능한 GitHub 저장소/관련 브랜치에서는 운영 Mac 프록시와 현재 스케줄 실행 코드를 찾지 못했다. 앱·Vercel API·발주 파서의 변경으로 서버 전체 복구 체계가 완성된 것은 아니다.

- **실행 목록 확정:** 수집 작업별 실행 명령, 입력/출력, launchd 주기, 제한 시간, 외부 계정, 소스 코드 위치를 한 표로 만든다. 꺼진 예전 GitHub Actions를 임의로 켜서 중복 실행하지 않는다.
- **작업 기록:** 매 실행에 `job_id`, `source`, `started_at`, `finished_at`, `status`, `last_success_at`, `attempt`, `error_code`, 입력/출력 건수를 남긴다. 실패 시 `last_success_at`과 정상 데이터를 유지한다.
- **중복 실행 제어:** 수집기별 잠금과 만료 가능한 실행 소유권을 둔다. 같은 작업이 실행 중이면 새 실행은 대기 또는 명시적 보류로 남긴다.
- **발행 분리:** 임시 수집 → 스키마/건수/중복 키/시각 검증 → 정상 스냅샷 발행 순서로 처리한다. 일부 실패 결과는 별도 격리하고 현행 데이터에 덮어쓰지 않는다.
- **재시도:** 읽기 수집은 지수 대기와 최대 시도 횟수를 둔다. 재고 변경처럼 외부에 반영될 수 있는 쓰기는 작업 ID와 결과 조회가 준비되기 전 자동 재시도하지 않는다.
- **상태 감시:** 수집 주기별 마감 시각과 마지막 성공 시각으로 지연을 판정한다. 로그 파일 수정 시각이나 HTTP 200만으로 성공을 판정하지 않는다.
- **장애 연습:** 터널 변경, 네트워크 단절, 수집 원본 누락, 디스크 쓰기 실패, 실행 중 서버 재시작을 각각 재현하고 정상본 유지·중복 반영 없음·복구 후 최종 값 확인을 통과해야 한다.

## 데이터 정리 순서

먼저 원본, 현재 검증본, 변경 이력을 분리해 백업한다. 그다음 상품/SKU/채널의 고유 키와 참조 관계를 조회해 중복·고아 행·잘못된 옵션 연결을 보고서로 만든다. 삭제나 합치기는 변경 전후 건수와 참조 영향을 확인한 별도 마이그레이션으로 진행한다. 이 PR은 운영 데이터를 삭제하거나 DB 구조를 이전하지 않는다.
