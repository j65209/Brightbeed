# Brightbeed 서버 컴퓨터에서 이어하기

2026-09-11 저장. 사용자는 현재 Mac에서 작업을 멈추고 실제 수집 서버 컴퓨터에서 이어가기로 했다.

## 사용자 목표와 우선순위

회사 앱 Brightbeed의 통신·30분 자동 수집·재고 저장·데이터 갱신을 안정화한다. 통신 실패를 동기화 완료로 표시하거나, 승인 후 실제 재고가 바뀌지 않는 문제를 해결하는 작업이다. 보안/인증 개편은 사용자가 이번 범위에서 뒤로 미뤘다.

현재까지 수정은 검토용 브랜치와 초안 PR에 저장됐다. 운영 main에 병합하거나 운영 서버에 배포하지 않았다. 실제 회사 재고를 테스트 목적으로 변경하지 않았으며, DB 구조 변경이나 데이터 삭제도 하지 않았다.

brightbeed-stock은 비공개 저장소이므로 기존 GitHub 계정의 접근 권한이 필요하다. 각 안정화 브랜치의 `docs/RELIABILITY.md`에 세부 변경, 적용 조건과 남은 한계가 있다. 이 인계 문서는 PR #3 브랜치에 추가 저장된다. 구현 커밋 이후 인계 문서 커밋이 있을 수 있으므로 최신 브랜치를 읽는다.

PR #2와 #3은 `agents.html`/`index.html` 일부가 겹친다. 둘을 무작정 덮어쓰지 말고 적용 순서를 정해 충돌 해결 후 재검증한다.

## 완료한 1차 변경

- 응답 본문까지 통신 제한 시간 적용. 터널 주소 캐시 만료와 읽기 1회 복구. 쓰기 자동 재전송 제거.
- 필수 동기화 작업의 결과를 모두 기다리고 실패·보류·확인 불가를 표시. 에이전트의 누락된 상태를 근무 중으로 표시하지 않음.
- 외부 플랫폼 매출 카드 30분 조회 포함. 벤더 원본 시각·재시도 간격 수정.
- JSON 저장 시 불러온 기준 내용과 현재 원격 내용 비교. 충돌 후 최신 SHA로 전체 파일을 다시 덮어쓰던 동작 제거.
- 발주 파서의 부분 오류·빈 결과·급감 차단, 실행 잠금, 이전 정상본 백업과 원자적 파일 교체.
- Supabase `{error}`를 DB 실패로 처리. 외부 반영 후 DB 실패 시 후속 채널 쓰기 중단.
- 케이블 마스터 변경 전 원본 재고 확인과 변경 후 재조회. Sixshop 결과까지 반영해 부분 실패와 알림 계산.
- 저장 실패·부분 성공·결과 누락 시 화면 입력 유지. 0 이상의 정수와 중복 없는 최대 20개 SKU 입력 검증.
- 수집 결과의 빈 값·해석 불가 수량·누락/중복 옵션·오래된 원본 차단. 등록 상태 전체 초기화 제거.
- 식스에이 옵션의 기존 외부 식별자 확인. 단종 유지에서 DB 캐시 0만 믿고 외부 호출을 생략하던 동작 제거.

## 검증 상태

- 앱: `node --test tests/reliability.test.cjs` — 14개 통과.
- 파서: `python3 -m unittest discover -s tests -p 'test_*.py'` — 5개 통과.
- 재고 API: `pnpm test` — 22개 통과.
- 재고 API TypeScript 검사와 `pnpm build` 통과. Next.js의 기존 middleware 이름 경고는 남아 있음.
- 합계 41개 테스트. 가짜 네트워크/DB 응답, 설치된 Supabase 쿼리 객체의 가짜 fetch, 임시 파일로 검증했다. 운영 재고를 쓰는 종단 간 검증은 아직 하지 않았다.

## 서버 컴퓨터에서 가장 먼저 할 일

1. 두 PR과 각 저장소의 `docs/RELIABILITY.md`를 읽고 기존 작업을 이어받는다. 안정화 1차를 처음부터 다시 만들지 않는다.
2. 서버의 실제 프록시/수집기 소스와 실행 설정을 읽기 전용으로 찾는다. 문서에 있던 후보 경로는 `~/server/brightbeed-proxy`다. 현재 존재 여부와 실제 실행 경로를 확인한다.
3. launchd 작업, 실행 프로세스, 작업별 주기, 로그, 입출력 파일, 마지막 시도/마지막 성공 시각을 대조한다. 환경 파일이나 로그의 비밀번호·토큰은 출력/공유하지 않는다.
4. 실행 중인 체크아웃의 변경 사항을 보존하고, 코드 수정·실패 재현은 별도 작업 폴더와 복사한 데이터로 준비한다. 현재 서버 파일을 무조건 git checkout/pull로 덮어쓰지 않는다.
5. 확인된 실제 서버 구조에 맞춰 아래 후속 작업을 구현하고 검증한다.

이전 컴퓨터에서는 접근 가능한 GitHub 저장소와 관련 브랜치를 찾아도 현재 운영 Mac의 프록시·스케줄 실행 코드를 확보하지 못했다. 예전 sixshop-collector GitHub Actions는 비활성 상태였다. 예전 작업을 임의로 켜 중복 수집을 만들지 않는다.

## 남은 핵심 작업

- **실행 기록과 상태:** 작업 ID, 시도/시작/종료, 성공/부분 성공/실패/미확인, 마지막 성공 시각, 오류 코드, 수집 건수를 영속 저장한다. 로그 수정 시각이나 HTTP 200만으로 성공으로 처리하지 않는다.
- **중복 실행·재고 중복 반영 방지:** 수집 작업 잠금, SKU별 실행 소유권, 요청 고유 키를 추가한다. 서버 인스턴스가 겹치거나 응답이 유실돼도 같은 재고 변경이 반복되지 않아야 한다.
- **원자적 데이터 발행:** 임시 수집 → 전체 검증 → 트랜잭션 발행으로 처리한다. 현재 1차 변경은 전체 원본 검증 후 쓰지만 여러 행 DB 변경 도중 장애가 나면 일부만 반영될 수 있다.
- **외부 결과 대조·복구:** 모든 판매채널의 실제 반영 값을 재조회한다. 외부 반영 이후 DB 실패나 시간 초과는 재전송 전 대조·복구한다. 케이블 마스터 재조회만으로 모든 채널의 일관성을 보장할 수 없다.
- **수집원 연결:** 식스에이의 오래된 JSON 기반 최신화 경로를 실제 정상 수집원에 연결한다. 여러 창고와 변경된 외부 옵션 식별자는 매핑을 확인한다.
- **데이터 정리:** 백업/복원 검증 → 중복 키·고아 행·잘못된 옵션 연결 읽기 전용 조사 → 건수/참조 영향이 있는 정리안 → 별도 마이그레이션 순서로 진행한다.
- **장애 연습:** 통신 단절, 터널 변경, 원본 누락, DB/디스크 오류, 동시 수정, 서버 재시작에서 정상본 유지·중복 반영 없음·복구 후 실제 값 확인을 검증한다.

발주 파서를 서버에 반영할 때는 `parse_orders.py`와 `snapshot_store.py`를 함께 배치해야 한다. GitHub 병합만으로 서버 실행 코드가 자동 갱신된다고 가정하지 않는다. 코드 롤백과 이미 외부에 반영된 재고 복구는 별개다.
