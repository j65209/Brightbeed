# 미루 업무 처리 구조

미루는 기존 `/agent/chat` 연결로 지시를 구조화한 다음, 실제 카탈로그에서 상품·옵션을 확인한다. 모델은 문장 해석만 담당한다. 저장 대상 식별자는 카탈로그에서 가져오고, 저장 승인은 현재 화면의 변경 제안과 연결한다.

## 동작

- 한글 수량, 상품·옵션 선택, “아까 그 상품”, 수량·옵션 정정을 처리한다.
- 조회 요청은 후보를 선택한 뒤에도 조회로 유지한다.
- 변경 직전 원본을 다시 조회한다. 승인 중 수량이 달라지면 새 제안을 만든다.
- 변경 승인은 한 번만 사용 가능하고 5분 뒤 만료된다. 이전 대화 버튼은 새 변경을 승인할 수 없다.
- 저장 요청을 자동 재전송하지 않는다. 응답이 없거나 실패하면 원본 재조회로 결과를 확인한다.
- 미확인 저장은 동일 탭의 sessionStorage에 남겨 새로고침 후에도 중복 전송을 방지한다. 서버 공통 작업 이력이나 다른 기기의 잠금 기능을 대체하지 않는다.
- 실제 수량이 목표와 일치하는 경우에만 확인 완료로 표시한다. 서버의 성공 문자열만으로 완료 처리하지 않는다.
- 다른 직원의 대화창을 열어도 처리 결과는 원래 담당 직원의 기록에 남는다.

## 기존 서버 계약

새 API 키나 별도 모델 계정을 추가하지 않는다.

| 경로 | 용도 | 기존 요청 형태 |
| --- | --- | --- |
| `POST /agent/chat` | JSON 문장 해석 | `{agent:"stock", text, history:[]}` |
| `GET /sx/catalog?brand=…` | 상품·옵션·현재 재고 확인 | 기존 카탈로그 응답 `products[]` |
| `POST /sx/update-brand-stock` | 확인한 재고 변경 | `{brand, updates:[{id,name,setStock,optionNo?,optionLabel?}]}` |

AI 대화는 기존 서버에서 마스터 권한을 요구한다. 조회 전용 계정은 해당 엔드포인트를 호출하지 않고 단순 검색을 사용한다. 마스터 계정의 모델 응답이 유효한 JSON이 아니거나 연결이 실패하면 제한된 문장 해석으로 전환하고 이를 알린다.

## 배포와 검증

`agents.html`과 `agents-stock.js`를 함께 배포해야 한다. 빌드 과정이나 새 의존성은 없다. `node --test tests/agents-stock.test.cjs`로 모의 카탈로그와 모의 AI 응답을 사용한 회귀 검증을 실행한다. 테스트는 실제 재고 저장을 호출하지 않는다.

### 실제 AI 연결 확인 (2026-09-11)

관리자 인증으로 문장 해석만 호출했다. 상품 카탈로그는 모의 데이터이며 실제 재고 저장 요청은 전송하지 않았다.

- 단독 해석 요청은 올바른 `add: 1` 응답을 67초 만에 반환했다.
- 수정본의 실제 프롬프트로 연속 5개 대화를 검사한 결과, 1개는 유효한 AI 해석을 반환했고 4개는 서버가 모델 응답 실패를 반환했다. 마지막 실패의 `fallbackReason`에서 `HTTP Error 429: Too Many Requests`를 확인했다.
- 정상 응답은 약 67초, 실패 응답은 약 55초가 걸렸다. 기존 25초 제한을 100초로 조정하고 대화창 진행 상태를 추가했다.
- 429가 확인되면 60초 동안 AI 재호출을 쉬고 기본 해석을 사용한다. 서버의 쿼터 문제를 해결하거나 쿼터 초기화 시점을 보장하는 기능은 아니다.
- 자동 회귀 검증 23개 통과. 실제 AI 연결의 안정성 및 실제 저장 장애는 별도 서버 조치가 필요하다.

## 서버에서 이어서 확인할 사항

이 공개 저장소에는 현재 터널에서 실행되는 프록시 서버 구현이 없다. 별도 `sixshop-collector` 저장소의 수집기와 GitHub Actions 스크립트는 확인했으나, 현재 `/agent/chat` 및 `/sx/update-brand-stock` 처리 서버와 같다고 확인되지는 않았다.

- 재고 변경 엔드포인트가 실제 상품과 옵션을 식별하고 저장하는지 확인해야 한다. 이번 수정은 해당 서버의 저장 로직을 대체하거나 우회하지 않는다.
- 서버 카탈로그가 캐시를 반환할 수 있다면 쓰기 직전·직후 확인은 원본 조회를 보장하도록 서버에서 구현해야 한다. 클라이언트의 `cache:no-store`는 서버 내부 캐시를 무효화하지 않는다.
- 다른 사용자·기기와 동시에 수정할 때의 원자적 증감, 요청 ID 중복 방지, 공통 변경 이력은 서버에서 처리해야 한다.
- 기존 클라이언트에 포함된 PIN은 이 변경에서 추가·교체하지 않았다. 서버의 사용자별 인증과 권한 검증을 별도로 유지·개선해야 한다.

실제 서비스 검증은 마스터 계정에서 조회 → 변경 제안까지 먼저 확인하고, 사용자가 지정한 상품·옵션·수량에 한해 저장과 원본 재조회를 확인한다.
